◆The assessment lifecycle

One pipeline, from picker to PDF

Most "steps" below are tabs on a single hub page (web.py:202), not separate screens. Dashed boxes are skippable — nothing downstream hard-requires them. The only two gates that block forward progress are the 80% completion gate before analysis, and the review-approval gate before any client-facing artifact can leave the building.

01Foundation

FrameworkRegistry + Unified Control Clusters

Two independent layers let one tool run six frameworks without duplicating scoring, UI, or questionnaire logic. FrameworkRegistry (registry.py:20) is a single in-memory catalog — every framework is forced into the same FrameworkDefinition shape (domains → sections → controls, each with a weight), so scoring code written for DPDPA works unmodified for ISO 27001, GDPR, or any other registered framework.

Unified Control Clusters are the second, separate layer: a hand-curated mapping (mappings/clusters.py) that groups semantically-equivalent controls across frameworks so one question can satisfy several frameworks' requirements at once — but only when 2+ frameworks are selected for the same assessment.

Adding a 7th framework

Write one definitions/xyz.py assembling a FrameworkDefinition (domains, sections, controls, weights, red-flag patterns), then register it in main.py:217. Scoring, PDF export, and the questionnaire builder need zero changes — they only ever talk to the registry's generic interface.

Boot-time safety net

_assert_framework_catalog_complete() fails the app's startup loudly if a registered framework ever drifts from the UI's enabled/roadmap tuples — a framework can never silently vanish from the picker.

02Phase 0

Scope & applicability

Five scope answers deterministically exclude requirement IDs — pure Python, no Claude call (scope_profiler.py:45-119). The bias runs toward inclusion: an "unsure" answer keeps a requirement in scope; only an explicit "no" excludes it.

company_size is accepted by compute_scope() but never read in the function body — exclusion is driven solely by the 5 SCP answers. And scope exclusion is currently a no-op for multi-framework assessments — every control from every selected framework appears regardless of scope answers.

03Evidence gathering

Desk review & document processing

Upload dispatches by file extension. PDFs and DOCX go through pdfplumber / python-docx text+table extraction; images have no OCR library — a live Claude vision call transcribes visible text and adds a short compliance summary instead. A scanned PDF that extracts to nothing gets HTTP 422, asking the user to re-upload as an image.

Word budgets, two layers

Per document: first 5,000 words (config.py:18), PDF/DOCX only.
Across all documents: 20,000 words total (config.py:19) — once exhausted, remaining documents are dropped entirely, not trimmed. Upload order decides what survives.

Two governing rules in the prompt

"Policy ≠ implementation" — a written policy alone can't score above partially-compliant without evidence of follow-through.
"Absence of evidence is evidence of absence" — silence on a requirement never becomes an assumed compliant.

one Claude call → coverage_summary, 4 levels per requirement
LevelMeaning
adequatewell-addressed by the documents
partialmentioned, but with gaps
absentexplicitly missing despite a relevant document existing
not_coveredno relevant document was uploaded at all

These four levels are entirely the model's judgment — CyberAssess never independently computes coverage from finding counts. Findings themselves persist as three types: evidence (quote, severity always "info"), absence (description, model-set severity), and signal (a red flag — GDPR/CCPA copy-paste, buried consent, template artifacts, missing breach timelines, scope gaps). A signal tied to several requirements is stored against only the first one (desk_review.py:218) — see gap #5.

04Phase 1

Context profiling

A 14-question, 4-block wizard feeds one Claude call (context_profiler.py) that derives a risk_tier (HIGH/MEDIUM/LOW), a priority_chapters order, and a likely_not_applicable list. risk_tier is the one piece that has real downstream teeth — it drives adaptive tiering (Part 06). The rest — relevance weights, context notes — is display-only metadata; nothing filters or reorders questions by it today.

05Phase 3 · optional

Domain screening

Nine broad questions (Consent, Notice, Purpose Limitation, Accuracy, Security, Breach Notification, Data Subject Rights, Governance/SDF/ Children, Cross-Border) feed one Claude call that infers a status + confidence for all 41 DPDPA requirements — any requirement the model misses is force-backfilled to not_assessed / low.

the confidence gate — same rule, applied twice
InferredDB auto-fill (once)Live re-modulation (every render)
compliant / partial · high confidence✓ persisted as answer✓ pre-filled, "inferred" badge
any status · low confidence—forced to "deepened"

Negative findings are deliberately never auto-filled, even at high confidence — a human has to type the "no" themselves.

06Assembly

Adaptive questionnaire & tiering

Recomputed fresh on every page load — nothing about the questionnaire's shape is persisted, only the underlying answers and findings. Desk-review modulation always overrides screening modulation, and within desk review, signals/absences always override a positive pre-fill: "documents describe intent, not operational reality."

07The engine

Gap analysis: the Claude calls

Scoring is never done by Claude (Part 08) — this stage's only job is to assign a compliance_status, risk_level, maturity_level, and remediation fields per requirement. The legacy DPDPA path is a genuine two-call pipeline; the multi-framework path is really N+2 calls, despite reusing the same evidence step.

08Pure arithmetic

Deterministic scoring

Scoring is intentionally never delegated to Claude — plain arithmetic over the compliance_status it assigned. risk_level and Claude's own maturity_level field play no role in this formula at all.

≠

What doesn't score: risk_level only drives a dashboard tally of critical/high gap counts. Claude's maturity_level (0–5) only feeds a separate cross-framework maturity view (compute_unified_maturity()) — a distinct concept from the 0–100 compliance score above. A newer cluster-verdict 0–5 scoring path exists in parallel but raises NotImplementedError for anything except ["dpdpa"] (see gap #3).

09Human in the loop

Review gate, RFI, follow-ups, remediation

The release gate

RFI generation

Eligible: gap items where status isn't compliant/not_assessed, plus desk-review absence findings, deduped by requirement ID only. One Claude call writes only the human-facing text — priority and deadline are deterministic:

Criticalrisk=critical, or non-compliant + priority≤11 wk
Highrisk=high, or non-compliant2 wk
Mediumpartially-compliant3 wk
Loweverything else4 wk

Regenerating deletes and replaces the prior RFI — no version history.

Follow-up questions

Whether to trigger is deterministic; the question text is Claude-generated. Strongest trigger (3 follow-ups): desk-review evidence exists but the answer claims no implementation — a direct contradiction. not_applicable is never followed up, regardless of contradicting evidence. Any failure degrades to zero follow-ups, never blocking the questionnaire.

Remediation status — no transition validation

Any status can follow any other via one PATCH; there's no state-machine guard, and no cross-check against review status.

open → in_progress → closed or accepted_risk

Only literal closed stamps a close date (once — re-closing won't reset it). accepted_risk is a parallel terminal state that never gets a close date, even though it's functionally resolved.

10Delivery

Reports & the web portal journey

The portal is effectively one HTMX hub page per assessment (web.py:202) — the pipeline diagram at the top of this page is the user's journey; each stage is a tab or an HTMX partial, not a separate navigation. The board-ready PDF assembles from the same gap_items/chapter_scores data used throughout, branching on just two flags — dpdpa_only and has_dpdpa — everywhere else it's fully generic across all six frameworks.

  1. Cover page — dynamic title, score ring, per-chapter bars.
  2. Executive dashboard — 4 KPI tiles, compliance distribution, chapter heatmap.
  3. Critical & high-risk gaps — filtered, sorted by risk then priority.
  4. Remediation roadmap — a 4-segment priority timeline.
  5. Strategic initiatives — only rendered if any initiatives exist.
  6. Appendix: findings by chapter — full evidence quotes for every non-compliant item.
  7. Scope, limitations & methodology — wording branches DPDPA-only vs. multi-framework.
🔒

Every download-producing endpoint — /report, /report/pdf, /rfi/pdf, /compare/* — is gated by the same require_review_approval() from Part 09. Framework availability is also a hard server-side check, not just a UI hint: submitting GDPR/HIPAA/PCI-DSS (roadmap-only) is rejected even if someone bypasses the disabled checkbox in the DOM.

!Surfaced during this trace

Known gaps & inconsistencies

Understanding the real algorithm means understanding where it's incomplete, not just where it works cleanly. None of these are hidden — they're listed here on purpose.

01

Multi-framework gets none of the adaptive machinery

Desk-review pre-fill, screening pre-fill, and adaptive tiering are entirely DPDPA-only-path features. A multi-framework questionnaire is uniformly active/standard regardless of uploaded documents or screening answers.

02

Scope exclusion doesn't apply to multi-framework questionnaires

The exclusion list is passed as None with a "for now" comment in the multi-framework builder.

03

The cluster-verdict scoring path is DPDPA-only

It raises NotImplementedError for any other framework selection — built, but not wired into the multi-framework router.

04

Coverage-guarantee reinstatement targets dead code

It un-skips desk-review-skipped questions, but _modulate_question no longer ever produces status="skipped" — only scope exclusion does, and that's explicitly excluded from reinstatement.

05

A multi-requirement signal is stored against only the first requirement

The questionnaire engine has to separately re-derive signal coverage via keyword matching on finding text to compensate.

06

company_size is accepted but never used

Scope exclusion is driven solely by the 5 scope answers.

07

Only IT/SaaS has a bespoke question bank

Every other industry — fintech, healthcare, e-commerce, etc. — uses the same 5-question generic bank today.

08

One document upload can bypass the 80% completion gate entirely

Independent of how much that document actually covers.

09

RFI regeneration has no version history

It deletes and replaces the prior RFI document outright.

10

Remediation has no transition validation or review cross-check

Any status can follow any other; closing remediation doesn't require the underlying finding to be reviewed/approved first.

11

One report endpoint still bypasses the registry shim

reports.py:8 imports directly from app.dpdpa.framework instead of going through compat.py or the registry — a residual pre-multi- framework seam.
