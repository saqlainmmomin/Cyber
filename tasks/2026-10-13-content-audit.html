Content audit: how the app's words are written

13 October 2026 · follows PR 141 (UI audit and Next.js migration plan), which set content aside as a separate track. Six read-only reviewers swept the code and the screens; this page combines their reports.

The short version

The interface is not the main problem. The content has no designed shape for its reader. Three things are missing, and one more is going wrong:

  1. A finding is never written down as a finding. There is no gap statement, no impact, no cause, no basis for the risk rating and no reasoning for the recommendation. The model is asked for some of them and the pipeline drops them.
  2. The same text is shown under different headings, with different names. The same three strings pass through five screens, and each uses its own words for outcome, risk, priority and "finding".
  3. Nothing changes shape for the reader. Board text, auditor text and client text come from the same fields. The client RFI is written in the auditor's voice. The in-app report is a table of 93 controls with a counts line on top.
  4. Some content is wrong. An issued board report calls itself a draft, the client RFI cites the wrong statute sections, and a score of 84% is labelled "Compliant" next to 17 high or critical gaps. A presentation-only Next.js port would carry these across.

Findings are rated P0 (reader cannot do the job, or the content is wrong), P1 (clearly below standard) or P2 (polish).
