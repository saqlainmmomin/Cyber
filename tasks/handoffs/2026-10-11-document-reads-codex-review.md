# Handoff: adversarial review of the "read on arrival" design (Codex)

## Goal
Review the design in `tasks/handoffs/2026-10-10-document-budget-design.md`, section `## Results`, against the actual codebase. Saqlain wants no surprises later: find everything the design missed, got wrong, or would break. Done means a `## Codex review` section appended to **this** file with a verdict and findings. This is a review, not a build.

## Rules
- Read-only. No code changes, no prompt edits, no commits, no pushes. The only file you write is this one.
- No live LLM or API calls. If you run tests, run them with `OPENROUTER_KEY=""` (never `env -u`).
- Never read `validation/companies/*/answer_key.json`.
- Every claim cites a file and line you actually read. If you could not verify something, say so; do not guess.
- Plain short sentences. No em dashes. No AI attribution anywhere.
- Read `CLAUDE.md` and `AGENTS.md` first for constraints and gotchas.

## What to check
1. **Every claim in the Results section about current behaviour.** Re-read each cited file and line. List any that are wrong or stale.
2. **Every path by which evidence becomes in scope for an assessment.** The design lists direct upload, magic-link linking, reuse and new versions. Find any others (API routes, scripts, demo loaders, legacy `AssessmentDocument`, archive or invalidate flows, evidence removed from scope). For each: does the design trigger a read, re-read or stale marking correctly?
3. **Every consumer of desk-review output.** `DeskReviewSummary`, `DeskReviewFinding`, `document_catalog`, `coverage_summary`, `raw_ai_response`, budget fields. Include routes, templates, pre-fill (`auto_answer.py`), the requirement card, the evidence page, follow-up generation, RFI generation, PDF/DOCX/XLSX/PPTX reports, report snapshots and scripts. For each: what breaks if desk review becomes a live view built from per-file reads?
4. **Every consumer of the gap-analysis extraction and the judge input.** Confirm the judge prompt can stay byte-identical when fed saved passages per control. Check the curated DPDPA single-framework path and its golden recordings.
5. **Conclusions, runs and locks.** `analysis_runs`, `Conclusion`, `ConclusionRevision`, `LOCKING_ACTIONS`, the compare-and-swap, citation storage per conclusion, report snapshots. Can a stale-only partial run fit the current model without breaking reports, history or tests? What has to change?
6. **Engagement-level evidence.** Uploads with `assessment_id=None`, evidence shared across assessments with different frameworks, framework added or removed after reads, archived or superseded versions. Does the per-(version, framework) read key hold up?
7. **Background work on SQLite.** How background tasks run today, session handling, write contention between a worker and web requests, restart behaviour. Is the proposed queue safe? What is the simplest safe shape?
8. **Tests and guards that will fail or must change.** Prompt fingerprint tests, budget-notice tests, desk-review tests, answer-key isolation, stale-path guards (`tests/yozora_paths.py`), golden recordings. List them with file and line.
9. **Reuse of parked v2 modules** (`app/services/grounding/chunking.py`, `metadata.py`). Any hidden coupling to v2 settings or to `ANALYSIS_PIPELINE_VERSION`?
10. **Cost and time estimates.** Check the arithmetic and the inputs (control counts, batch counts, the price source). Flag anything implausible.
11. **The staged PR plan.** Is each step independently shippable and safe behind its setting? Is anything in the wrong order? Is any step too big to review?
12. **Anything else** that would cause a complication later: migrations, data backfill for existing assessments, the demo seed and Veldhara scripts, Docker, the Bedrock migration plan, D1 to D11 and E1 to E6 decisions.

## Report back
Append `## Codex review` to this file:
1. Verdict: **GO**, **GO with changes**, or **NO-GO**, in one sentence.
2. Findings table: severity (blocker, major, minor), what is wrong or missing, file and line, and the concrete change to the design.
3. Claims in the Results section that you confirmed, as a short list.
4. Open questions you could not settle from the code.

### Runs, prompts and arithmetic

Partial conclusion history fits the existing schema. `record_framework_run` loops over returned assessments and records a revision, run id and citations for each at `app/services/analysis_pipeline.py:362`, `:422`, `:432`. Untouched conclusions are not removed there. Workpaper and cards already resolve each proposal's own run at `app/services/workpaper.py:155` and `app/services/requirement_card.py:260`. Extend run envelopes with target ids, reader identity, exact sent/omitted passages and input fingerprints. Whole-framework report persistence is the separate incompatibility in F1.
