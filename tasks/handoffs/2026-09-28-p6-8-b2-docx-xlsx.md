# P6-8 B2: DOCX + XLSX deliverables derived from the board report snapshot `[AR: write-once + derived-only + formula injection]`

Consultants and client teams get an editable Word version of the board report and an Excel workbook: framework summary, requirement register, top risks, action tracker, evidence register, and, when present, the prior-period changes and the ISO Statement of Applicability. Both files are derived **only** from a `board_report` version's stored, hash-checked JSON sidecar (B1, PR #80; schema v2 from P6-9, PR #86). They are rendered on request, never stored, and byte-deterministic. They touch the database only to load the snapshot row and its generated audit event. So the DOCX and XLSX always match the PDF of that version.

## Goal

1. `GET /api/assessments/{aid}/snapshots/{sid}/docx` and `…/xlsx` return a DOCX / XLSX for any `board_report` version of schema 1 or 2, rendered only from `read_board_report_document(db, snapshot)`.
2. Same document + same code = same bytes, whatever the wall clock.
3. The versions page shows "DOCX" and "XLSX" links on each board report row.
4. Devanagari and ₹ round-trip exactly (DOCX and XLSX store text, not glyphs).
5. No formula can execute from any cell, and XML-illegal control characters never crash an export.
6. The DOCX has the same sections, in the same order, as the PDF of that document's schema. The XLSX carries the working registers, plus the SoA with the consultant's recorded justifications.

## Decisions

### D-P6-8-B2-A: Derived artefacts, not snapshot types; rendered on request, never stored
- DOCX/XLSX are **not** new snapshot types and write **no** file, row or audit event. The authoritative, write-once artefact stays the board PDF + sidecar; the exports are a pure function of that sidecar.
- Why: storing would need new write-once plumbing and new metadata keys (B1 scenario 8 pins them exactly), and would not exist for already-generated versions. The RFI DOCX precedent works the same way.
- Consequence: if exporter code changes later, a re-download of an old version can differ. That is accepted and made visible: every export carries `EXPORT_FORMAT_VERSION` (About sheet, response header). Decided, see K1.
- No release gate on download (like the `/file` route): an existing version stays downloadable after the assessment is reopened.

### D-P6-8-B2-B: Inputs
- The route may read exactly: `load_snapshot`, `read_board_report_document` and `generated_event(...)["document_sha256"]`. Nothing else from the DB.
- `board_exports.py` itself has no DB access at all. Scenario 10:
  - bans `Session`, `app.models`, `build_document`, `approved_report`, `report_content`, `report_basis`, `conclusion_review`, `workpaper` and LLM tokens from its source;
  - allows `app` imports only from `board_report` and `report_snapshots`. So no `soa`, `remediation_groups` or `prior_period`: the SoA, groups and comparison are read from the document, never recomputed.
- Filename, labels and all content come from the document, so renaming the client after generation changes nothing (scenario 4).

### D-P6-8-B2-C: Module `app/services/board_exports.py` (new)
```python
EXPORT_FORMAT_VERSION = 1
SUPPORTED_SCHEMA_VERSIONS = (1, 2)
DOCX_MEDIA_TYPE = "application/vnd.openxmlformats-officedocument.wordprocessingml.document"
XLSX_MEDIA_TYPE = "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet"
DERIVATION_LABEL = ("Derived from board report snapshot {snapshot_id8}, {version_label} (document SHA-256 "
                    "{sha_prefix}). Edits to this file do not change the report version it was derived from.")
UNSUPPORTED_DOCUMENT_MESSAGE = ("This report version's document format cannot be exported to DOCX or XLSX "
                                "by this version of CyberAssess. The report version is unchanged.")
DOCX_BODY_FONT = "Noto Sans"
DOCX_COMPLEX_SCRIPT_FONT = "Noto Sans Devanagari"
FORMULA_PREFIXES = ("=", "+", "-", "@", "\t", "\r")
XLSX_SHEETS = ("About", "Framework summary", "Requirement register", "Top risks", "Action tracker", "Evidence register")
XLSX_OPTIONAL_SHEETS = ("Prior-period changes", "Statement of Applicability")   # v2 only, conditional, this order
XLSX_COLUMNS = {...}        # exactly as in the test file (7 sheets with columns; About has none)
DOCX_TABLE_HEADERS = {...}  # exactly as in the test file (same headers as the PDF template)
ROADMAP_INTROS = {1: "<B1 roadmap intro>", 2: "<the live template's roadmap intro>"}   # scenario 1 pins both
JUSTIFICATION_STATUS = {True: "Recorded", False: "Missing"}
MISSING_FILL = "FFFFF2CC"   # ARGB; fill on "Missing" status cells (an extra cue, never the only one)

class UnsupportedDocument(report_snapshots.SnapshotError): status_code = 409

def derivation_label(document: dict, document_sha256: str) -> str   # sha_prefix = sha[:board_report.SHA_PREFIX_CHARS]
def export_filename(document: dict, extension: str) -> str          # f"{company_name}_board_report_{version_label}_{id[:8]}.{ext}"
def render_docx(document: dict, *, document_sha256: str) -> bytes
def render_xlsx(document: dict, *, document_sha256: str) -> bytes
```
- Both renderers first check `document["schema_version"] in SUPPORTED_SCHEMA_VERSIONS`, else raise `UnsupportedDocument(UNSUPPORTED_DOCUMENT_MESSAGE)` before any output (D-P6-8-B2-J).
- Import `openpyxl` and `docx` **inside** the render functions (scenario 10 rejects a top-level `openpyxl` import), so the app starts even if openpyxl is missing.
- May import `display_date` and `SHA_PREFIX_CHARS` from `app.services.board_report` (read-only; do not edit that module).
- One private `_clean(text)` strips the XML-illegal characters `[\x00-\x08\x0b\x0c\x0e-\x1f]` from every string written to either format. Otherwise python-docx raises `ValueError` and openpyxl raises `IllegalCharacterError`.
- `None` renders as `""` in DOCX and as an empty cell in XLSX, never as the string "None".

### D-P6-8-B2-D: DOCX content (mirrors the PDF template of the document's schema)

**Styles and fonts.** The `Normal` style has `font.name = DOCX_BODY_FONT` and `rPr/rFonts` `w:cs = DOCX_COMPLEX_SCRIPT_FONT`. Word shapes Devanagari with the complex-script font; on Windows it falls back to Nirmala UI/Mangal if Noto is absent. No fonts are embedded.

**Body order.** Strings are identical to the PDF template wherever the PDF has them.

1. **Derivation label**: one paragraph, small italic. It appears exactly once, before "Management summary".
2. **Cover**, then a page break:
   - `Title` "Board report";
   - company name;
   - engagement (if any);
   - `Frameworks: name (version), …`;
   - `Assessment period: {period_label} | Evidence cut-off: {cutoff_label}`;
   - `Report generated: {generated_on}`;
   - `Version {vN} | Snapshot {id8}`;
   - the release line, if `released_by`;
   - `issue_status`.
3. **`Heading 1` sections**, in exactly this order:
   - "Management summary", "Top risks", "Remediation roadmap", "What we could not assess";
   - one section per framework, titled `"{name} ({version})"`;
   - **"Prior-period comparison" (schema ≥ 2 only)**;
   - "Sign-off", "Appendix A: Methodology", "Appendix B: Requirement register", "Appendix C: Evidence register";
   - **"Appendix D: Statement of Applicability" (schema ≥ 2 and `document["soa"]` set)**.

   The subsections are `Heading 2`: `Basis of assessment`, `Scope`, `Limitations`, `Confidentiality`, `Scores and coverage`, `Insufficient evidence`, `Request for information`, `Domains`, `Gaps`.
4. **Top risks.** Each risk is a `Heading 2` `"{rank}. {title}"`, followed by the lines the PDF prints: the description, the meta line, one paragraph per citation `"{filename} v{n}, {location_ref} (SHA-256 {prefix})"`, the owner/target line and the action line. If there are none: "No approved findings are recorded."
5. **Remediation roadmap.** The intro paragraph is `ROADMAP_INTROS[schema_version]`.
   - **v1**: one table with header `DOCX_TABLE_HEADERS["roadmap"]` over `roadmap.actions`; the Closes cell is `"{fw}: {req} ({finding})"` joined with "; ".
   - **v2**: for each `roadmap.groups` entry, in document order:
     - a `Heading 2` with the topic;
     - the headline paragraph;
     - a `roadmap_group` table (`Action | Owner | Target date | Status | Finding`) over `group.actions`, with the finding cell `"{framework_name}: {requirement_id} ({finding_title})"`;
     - a paragraph `"Findings addressed: " + "; ".join("{fw}: {req} ({finding})" for close in group.closes)`.

     The v2 export never uses the v1 flat table.
   - Empty state for both versions: "No remediation actions are recorded for the approved findings yet."
6. **Prior-period comparison** (v2), from `document["prior_period"]` only:
   - `status == "compared"`:
     - the `intro`;
     - `"Compared with version {prior.version_label} (snapshot {prior.snapshot_id[:8]}) for the assessment period {prior.period_label}, evidence cut-off {prior.cutoff_label}, generated {prior.generated_on}."`;
     - each note as a paragraph;
     - a `comparison` table with one row per `frameworks[]` entry:
       - compared: `name`, `prior_score` or "Not scored", `current_score` or "Not scored", `f"{score_delta:+.1f} points"` or "Not compared", then `counts` improved / regressed / changed / new / no_longer_assessed as strings. Scores use `str(value)`, as Jinja prints them.
       - not compared: `name` plus the other 8 cells **merged into one** reading "Not compared" (the PDF's `colspan`).
     - `"Gaps identified: {totals.prior.gaps} in the prior period, {totals.current.gaps} in this period."`;
     - then either a `comparison_changes` table (`"{framework_name}: {requirement_id} - {requirement_title}"`, prior and current labels or "Not assessed", `direction_label`) or "No requirement outcome changed between the two periods."
   - Any other status: each note as a paragraph, and no tables.
7. **Appendix D** (v2 with `soa`):
   - `intro`, `reliance`, then each note as a paragraph;
   - a `soa` table with one row per `soa.rows`: `"{reference} {title}"`, theme, `applicability_label`, `implementation_label`, and `justification` or "Justification not recorded" (as in the PDF).
8. **Other tables.** Each table's header row is `DOCX_TABLE_HEADERS`:
   - scores, under Scores and coverage;
   - per framework: one domains table, plus one gaps table when gaps exist;
   - the requirement register;
   - the evidence register.

   Cell text follows the PDF rules: dates via `display_date`; the fallbacks "Not recorded", "No target date" and "Unassigned"; `v{n}`; "Yes"/"No"; `citation or citation_note`.
9. **Empty states.** Empty-state sentences are as in the PDF.

**Header and footer.** Header `"{firm_name} | Board report"`, footer `"{company_name} | {version_label}"`.

**Core properties.**
- `title = f"Board report: {company_name}"`, `author = last_modified_by = firm_name`, `comments = label`, `identifier = snapshot.id`, `subject = f"Board report {version_label}"`, `revision = 1`.
- `created = modified = generated_at` (UTC, naive).
- Do not set `last_printed`.

B2 adds no copy of its own beyond the label, the roadmap intros and the headings. Everything framework-specific comes from the (already conditional) document. Scenario 9 checks an ISO-only export; scenario 9b checks that a DPDPA-only export has no SoA.

### D-P6-8-B2-E: XLSX content

**Sheet order:** `XLSX_SHEETS`, then (v2 only) "Prior-period changes" if `prior_period.status == "compared"`, then "Statement of Applicability" if `document["soa"]` is set. A sheet that doesn't apply is omitted, not left empty.

| Sheet | Rows |
|---|---|
| About | A1 = the derivation label; row 2 blank; from row 3, key/value pairs in exactly this order: Company, Engagement, Frameworks (`name (version)` joined "; "), Assessment period, Evidence cut-off, Report version, Snapshot ID, Report generated (`snapshot.generated_at` ISO string), **Prior-period comparison**, Document SHA-256 (full), Document schema version (int), Export format version (int). Prior-period comparison is: v1 → empty cell; compared → `"Compared with version {prior.version_label} (snapshot {prior.snapshot_id[:8]})"`; otherwise → `" ".join(prior_period.notes)` |
| Framework summary | one row per `summary.frameworks`: name, version, **pack version** (both from `frameworks`; `pack_version` is empty for v1 or when unrecorded), score (number or empty), rating, headline, then coverage in_scope / compliant / partially_compliant / non_compliant / insufficient_evidence / not_applicable |
| Requirement register | one row per register row: framework **name**, requirement_id, requirement_title, domain_title, outcome_label, risk_level, priority (number), decision_label, decided_by, decided_on (date cell), `citation or citation_note` |
| Top risks | one row per `top_risks` (the document caps it at 10; K2): rank, title, description, severity, priority, framework_name, requirement_id, requirement_title, outcome_label, citations joined "; " (empty when none), owner, target_date (date cell), action_title |
| Action tracker | one row per `roadmap.actions` entry, in document order (flat, target-date order, both schemas): title, owner, target_date (date cell), status_label, then the `closes` framework names / requirement ids / finding titles, each joined "; "; then **Control group**; then the two empty client columns "Client update" and "Evidence of closure". Control group is the `topic` of the `roadmap.groups` entry whose `closes` contain the action's `(framework_name, requirement_id)`, with distinct topics joined "; ". It is empty for v1. Group membership is by requirement (D-P6-9-F), so this lookup is exact without an action id. |
| Evidence register | filename, version_number (number), sha256_prefix, added_on (date cell), status, "Yes"/"No" |
| Prior-period changes | one row per `prior_period.changes` entry, in document order: framework_name, requirement_id, requirement_title, `prior_outcome_label or "Not assessed"`, `current_outcome_label or "Not assessed"`, direction_label |
| Statement of Applicability | see below |

**Statement of Applicability sheet (Saqlain, 2026-09-30).**
- The consultant-recorded justifications from the document (`soa.rows[].justification`, written by `soa.record_justification`) are exported as recorded. The Justification cell is blank only where none is recorded.
- Rows 1..n in column A hold `soa.notes` in document order: the PDF's notes, including `soa.MISSING_JUSTIFICATION_NOTE` ("{count} control(s) have no recorded justification.") when any are missing. Then one blank row, then the header, so the header is on row `n + 2`. With no notes, the header is on row 1.
- Columns: Control ID, Reference, Control, Theme, Applicability, Implementation, Justification, **Justification status** (`JUSTIFICATION_STATUS[bool(justification)]`: "Recorded" or "Missing", filterable), Justified by, Justified on (date cell).
- "Missing" status cells also get a solid `MISSING_FILL` fill. The word is the flag and colour is only an extra cue, so the sheet never relies on colour alone.

**Every table sheet:**
- the header row is bold;
- `freeze_panes` is the row below the header;
- `auto_filter.ref = f"A{header}:{last_column}{max_row}"`, which equals `ws.dimensions` wherever the header is on row 1.
- No formulas anywhere.
- No per-framework sheets: framework names contain `/` and `:`, which are illegal in sheet names, and the autofilter gives the per-framework view.

**Dates** are `datetime.date` values with `number_format = "yyyy-mm-dd"`.

**Workbook properties:** `creator = lastModifiedBy = firm_name`, `title = f"Board report: {company_name}"`, `description = label`, `identifier = snapshot id`, `created = modified = generated_at` (UTC, naive).

**Devanagari/₹** are plain Unicode strings; nothing special is needed.

### D-P6-8-B2-F: Determinism
- A private `_pin_package(content: bytes, generated_at: datetime) -> bytes` is used by both formats. It rewrites every zip entry in order with `ZipInfo(name, date_time=generated_at.timetuple()[:6])`, `ZIP_DEFLATED` and the same `external_attr`. For `docProps/core.xml`, it replaces the text of `<dcterms:created …>` and `<dcterms:modified …>` with `generated_at.strftime("%Y-%m-%dT%H:%M:%SZ")`.
- Why the core.xml rewrite: openpyxl 3.1.5 **overwrites `modified` with now() on save** (probed), even when it is set, and python-docx stamps zip members with the wall clock (the P5-6 flake). Do not edit or import `rfi_export._stamp_zip_entries`: rfi_export.py is frozen, and that function does not fix core.xml.
- `generated_at` = `datetime.fromisoformat(document["snapshot"]["generated_at"])` converted to UTC, with tzinfo dropped.

### D-P6-8-B2-G: Routes and the versions page
Append to `app/routers/snapshots.py`:
```python
@router.get("/{assessment_id}/snapshots/{snapshot_id}/docx")
@router.get("/{assessment_id}/snapshots/{snapshot_id}/xlsx")
```
The two routes share one helper:
1. If `db.get(Assessment, aid)` is None → `_error(404, "Assessment not found")`.
2. In one `try`: `load_snapshot` (404 for another assessment's id), then `read_board_report_document` (404 wrong type, 500 integrity), then `generated_event(db, sid)["document_sha256"]`, then the renderer (409 `UnsupportedDocument`). On `except report_snapshots.SnapshotError`: `db.rollback()`, then `_error(exc.status_code, exc.message)`.
3. `db.rollback()` (read-only), then return `Response(content, media_type=…, headers={"Content-Disposition": attachment_disposition(export_filename(document, fmt)), "X-Board-Document-Sha256": sha, "X-Board-Export-Format-Version": "1"})`.

No POST, no write, no audit event, and no `.unlink(` or `.commit(` added to the router.

In `app/templates/pages/report_snapshots.html`, inside the File cell after the existing Download link, when `row.snapshot.type == 'board_report'`, add `<a data-board-export="docx" href="/api/assessments/{{ assessment.id }}/snapshots/{{ row.snapshot.id }}/docx" …>DOCX</a>` and the same for `xlsx`, styled like the Download link. Nothing is added on other rows. Links appear on v1 rows too, since v1 exports (J).

### D-P6-8-B2-H: Formula injection (OWASP) and illegal characters
- Any XLSX string cell whose value starts with one of `FORMULA_PREFIXES` is written with `cell.data_type = "s"` **and** `cell.quotePrefix = True`, Excel's native "this is text" flag (the hidden apostrophe). The visible text is unchanged, and no `<f>` element can ever be written. Other string cells do not get `quotePrefix`.
- Every string cell is set with `data_type = "s"` after assignment; otherwise openpyxl turns `"=…"` into a formula (probed).
- This applies to every user-controlled string, including SoA justifications (free text). Scenario 7 plants one.
- Decided (K3): no visible apostrophe.
- DOCX has no formulas; text is written as-is after `_clean`.

### D-P6-8-B2-J: Supported schemas (1 and 2), and the rule for later bumps
- `SUPPORTED_SCHEMA_VERSIONS = (1, 2)`. v1 sidecars were issued before #86, and a version stays exportable as long as its sidecar is intact (Saqlain, 2026-09-30).
- Branch on `document["schema_version"]`, **not** on key presence:
  - **v1** renders the B1 layout: flat roadmap with `ROADMAP_INTROS[1]`; no comparison section; no Appendix D; no optional sheets; empty Pack version, Control group and About "Prior-period comparison" cells.
  - **v2** reads `prior_period`, `soa`, `roadmap.groups` and `frameworks[].pack_version` with `[...]`. A v2 document missing one is a builder bug and raises `KeyError` (a 500); it is never rendered partially. Scenario 11 checks this.
- Any other version → `UnsupportedDocument` (409) before output (scenario 6).
- **Rule for P6-10 and later:** a PR that bumps `DOCUMENT_SCHEMA_VERSION` must add the new version to `SUPPORTED_SCHEMA_VERSIONS`, render its new keys, and keep every earlier version rendering as before. Scenario 1 asserts the builder's current version is in the tuple, so a bump without B2 support fails CI.

### D-P6-8-B2-K: Former open questions, decided by Saqlain 2026-09-30
1. **Exports are re-rendered on each download, not frozen at issue time.** They are always rendered from the frozen, hash-checked sidecar through `read_board_report_document`, never from live assessment data. So the DOCX and XLSX always match the PDF of that version. An exporter code change shows up as a new `EXPORT_FORMAT_VERSION`.
2. **"Top risks" sheet, not a full findings sheet.** The document stores `top_risks` (capped at 10), not every approved Finding. The full gap list is in "Requirement register", and every Finding with an Action is in "Action tracker". A full `findings_register` would be a later schema bump.
3. **Formula injection uses `quotePrefix`**, not a visible apostrophe (D-P6-8-B2-H).
4. **No import of client edits.** The tracker's "Client update" and "Evidence of closure" columns are for the client, and consultants re-key updates into Actions. Any XLSX import would be a separate, reviewed task.
