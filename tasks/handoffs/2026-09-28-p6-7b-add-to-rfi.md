## Goal

1. **Available.** On a **v2** card, every missing-evidence entry shows:
   - its prefilled request text
   - an **Add to draft RFI** button, which posts one HTMX request and swaps the card
2. **Add.** A click writes one append-only audit event and changes nothing else:
   - no `Conclusion` change, no revision, no approval effect
   - no migration and no new table
   - no LLM call
3. **Idempotent.** A second click on an active request writes nothing.
4. **Removal.** **Remove from draft RFI** appends a withdraw event. It works from the card and from the RFI page.
5. **Draft.** The draft RFI (`rfi_requests.build_rfi_document`, which feeds the RFI page preview and the next generated version) gains one `evidence_request` item per requested document type, appended after the existing items.
   - `current_source` gains an `evidence_requests` key, and `schema_version` becomes 2, **only when a request is active**.
   - With no active request, the document and source are byte-identical to P5-6. Existing drafts, pins and issued versions are untouched.
6. **Issue.** A request reaches the client only after a new version is generated and issued. A draft generated before the add is stale (P5-6 `RFI_STALE_MESSAGE`). Issued versions stay write-once. The card then shows "Sent in RFI vN as RFI-00x".

## Design

### D-P6-7b-A: The draft RFI is derived; requests are append-only audit events, not a table

No new table or column, so there is no migration (the Alembic head stays `8b2d5f7e1c34`, pinned in ten test files). Requests follow the P6-6 report-basis and P6-7a acknowledgement pattern:

| Event | `action` | `entity_type` / `entity_id` | `metadata_json` (`sort_keys=True`) |
|---|---|---|---|
| Add | `rfi.evidence_requested` (`REQUESTED_ACTION`) | `"conclusion"` / conclusion id | `{request_key, framework_id, requirement_id, document_type, title, request, analysis_run_id}` |
| Withdraw | `rfi.evidence_request_withdrawn` (`WITHDRAWN_ACTION`) | `"conclusion"` / conclusion id | `{request_key, document_type}` (copied from the latest requested event) |

- `actor = conclusion_review.reviewer_actor(reviewer_name)`.
- **Active.** A request `(conclusion_id, request_key)` is active when the latest of its events (ordered by `created_at`, then `audit_events.rowid`) is `REQUESTED_ACTION`.
- **Frozen text.** `title` and `request` are frozen in the event at click time. The draft uses the frozen text, never a recomputation, so re-analysis cannot silently change a request the consultant already approved by clicking (scenario 9).
- **Why not a draft-RFI item table.** The P5-6 RFI has no mutable draft. Every version is a derived, write-once snapshot, and "draft" means "what the next generate would produce". Requests are therefore one more *input* to that derivation, like approved Conclusions and the scope checklist.

### D-P6-7b-B: Request identity and idempotency

- **The key.** `request_key(framework_id, requirement_id, document_type, detail) = sha256("\x1f".join((framework_id, requirement_id, document_type, " ".join(detail.split())))).hexdigest()[:16]`.
  - `detail` is the entry's `what_it_would_show`.
  - The key is stable across renders and across re-runs that produce the same entry.
  - It separates multiple `"other"` entries on one card.
- **Add is idempotent.** If the request is already active, `record_request` returns `(latest_event, False)` and writes nothing. The toast is `ALREADY_TOAST`.
- **Withdraw is idempotent.** If the latest event is a withdraw, it returns `(None, False)` and writes nothing. The toast is `ALREADY_WITHDRAWN_TOAST`.
- A key with no event at all is a 404, `RFI_REQUEST_NOT_FOUND_MESSAGE`.
- **Re-add** after a withdraw appends a new requested event. History is never updated or removed.

### D-P6-7b-C: Eligibility (server-side, from the card)

`requirement_card.add_rfi_request(db, *, assessment_id, conclusion_id, request_key, actor) -> tuple[AuditEvent, bool]`:

1. Unknown Conclusion, or one from another assessment → `RfiRequestError(CONCLUSION_NOT_FOUND_MESSAGE, 404)`.
2. It builds the card for the Conclusion's latest `proposed` revision with `card_for(db, conclusion, _latest_proposal(db, conclusion.id))`. If `card.source != "v2"`, or no `card.missing_evidence` row has `request_key == request_key` (an empty key never matches) → `RfiRequestError(RFI_REQUEST_STALE_MESSAGE, 409)`.
3. Otherwise it calls `rfi_evidence_requests.record_request(...)` with that row's `document_type` and `request_text`, `title=request_title(framework_id, document_type)`, and `analysis_run_id=card.analysis_run_id`.

The form sends only the key; text and eligibility are recomputed on the server, so a forged form cannot inject text. Other rules:
- **Any Conclusion state is eligible** (pending, approved, rejected). Asking for evidence is not a decision. It creates no revision and no version bump (D3 unaffected, scenario 2).
- **v1 cards get no add control** (D-P6-7b-J, Open question 1). v1 DPDPA has no pack requests, and v1 ISO/NIST entries are already on the scope checklist.

### D-P6-7b-D: Prefilled text (deterministic, no LLM)

```
REQUEST_TEXT_FORMAT = "{detail} Requested for {framework_name} {requirement_id}: {requirement_title}."
```

- **detail**, in this order:
  1. the normalised `what_it_would_show` (whitespace collapsed)
  2. if that is empty, the pack's `EvidenceRequest.reason` for that `document_type` in that framework
  3. otherwise `REQUEST_DETAIL_FALLBACK = "Provide this document."`

  A trailing `.` is appended if `detail` does not end in `.`, `?` or `!`.
- **framework_name** is `FrameworkRegistry.get(fw).name`, or `fw.upper()` for an unknown framework. **requirement_title** is the control's `title`, or the id.
- **title** (the RFI item title) is `request_title(framework_id, document_type)`:
  - `RFI_OTHER_TITLE = "Additional evidence"` for `"other"`
  - else the pack's `EvidenceRequest.label`
  - else `document_type.replace("_", " ").capitalize()`

  This matches P6-7a's card label except for `"other"`.
- **Why no LLM.** `what_it_would_show` was produced by the judge at analysis time. It is already shown on the card, and the exact text the RFI will carry is shown in `data-rfi-request-preview` before the click. The click is the consultant's review of that text (D-P6-F: no *unreviewed* LLM text in a client document). A new LLM call would add cost and non-determinism for no gain. Editable text is Open question 2.

### D-P6-7b-E: How requests enter the RFI document (`rfi_requests.py`)

- **Source.** `current_source` builds the four P5-6 keys as today. Then, if `active_requests(db, assessment.id)` is non-empty:
  - set `source["schema_version"] = RFI_REQUESTS_SCHEMA_VERSION` (2)
  - set `source["evidence_requests"] = sorted([conclusion_id, request_key] ...)`

  With no active request, the source is byte-identical to P5-6 (scenarios 4 and 10).
- **Document.** `build_rfi_document` keeps the document and requirement items unchanged and numbered first. It then appends `rfi_evidence_requests.rfi_items(active_requests(...))`, each prefixed with the next `item_id`. Other fields:
  - `schema_version` is `source["schema_version"]`
  - `totals["requirements"]` counts only `kind == "requirement"`
  - `totals["evidence_requests"]` is added **only when > 0**
  - the top-level key set is unchanged
- **`rfi_items(requests)`** produces one item per `document_type`, in order of first appearance in `active_requests`. `active_requests` is ordered by each key's **latest** event, so a re-added request moves to the end. Each `"other"` request is its own item. Item shape:
  ```
  {"kind": "evidence_request", "title": first request's title,
   "request": " ".join(unique request texts, in order), "required": True,
   "requirements": unique [framework_id, requirement_id] pairs, in order,
   "document_type": ..., "control_reference": None, "conclusion_id": None,
   "conclusion_version": None, "group": "Additional evidence requested",
   "request_refs": [[conclusion_id, request_key], ...]}
  ```
  One document requested for DPDPA and ISO becomes one item, matching the RFI introduction's "only needs to be provided once" (scenario 6).
- **Not merged with checklist `document` items of the same type** (Open question 3). The targeted item says specifically what the document must show.
- **`render_items`.** It treats `evidence_request` like `document` (`requirement_id ""`, the `requirements` id list), with `current_status = RFI_EVIDENCE_REQUEST_STATUS`. `rfi_export` is untouched, and the PDF groups the item under its `group` (scenario 5).
- **`page_context`** adds `"evidence_requests": active_requests(db, assessment.id)` and `"evidence_requests_note": RFI_PAGE_REQUESTS_NOTE`.
- **Source guards still hold.** `rfi_requests.py` still contains no `delete` or `.commit(`, and `GapReport` appears exactly twice.

### D-P6-7b-F: Card states and markup (`components/requirement_card_body.html`)

**New fields.** `MissingEvidence` gains four trailing defaulted fields: `request_key: str = ""`, `request_text: str = ""`, `rfi_state: str = ""` and `rfi_status_label: str = ""`. `RequirementCard` gains one trailing field, `other_rfi_requests: tuple = ()`. `CardContext` gains `rfi_states: dict = field(default_factory=dict)`, filled in `load_context` by `rfi_evidence_requests.request_states(db, assessment, ids)`: one events query, plus at most one issued-RFI sidecar read, and only when requests exist.

**States.** On v2 cards, each entry has `rfi_state`:
- `available`: no active request
- `requested`: active, and not in the current issued RFI
- `issued`: active, and its `[conclusion_id, request_key]` is in a `request_refs` of the **current issued** RFI document

Issued-state lookup uses `current_rfi_issue` plus `read_rfi_document`. On a `SnapshotError`, it treats the request as not issued. The version label is `f"v{sequence}"` from `rfi_snapshot_rows`.

**Markup, v2 only.** v1 and `none` entries keep P6-7a markup exactly. The section renders when `requirement.missing_evidence or requirement.other_rfi_requests`.

- The `<li data-missing-evidence="{document_type}">` gains `data-rfi-request-key="{key}" data-rfi-state="{state}"`. It contains no nested `li`.
- **`available`:**
  - `<p data-rfi-request-preview>{request_text}</p>`
  - `<form data-rfi-add-form hx-post="/api/assessments/{aid}/rfi-requests/{cid}" hx-target="#conclusion-card-{cid}" hx-swap="outerHTML" hx-include="#reviewer-name">` containing `<input type="hidden" name="request_key" value="{key}">` and a button labelled `Add to draft RFI`
- **`requested` / `issued`:**
  - `<p data-rfi-request-status>{rfi_status_label}</p>`, where the label is `STATE_REQUESTED_LABEL` or `STATE_ISSUED_LABEL.format(version_label=, item_id=)`
  - `<form data-rfi-withdraw-form hx-post=".../rfi-requests/{cid}/withdraw" ...same target/swap/include>` with the hidden `request_key` and a button labelled `Remove from draft RFI`
- **Orphans.** `other_rfi_requests` holds the active requests whose key is no longer in the card's missing list (after re-analysis), in `active_requests` order. They render under `OTHER_REQUESTS_LABEL` as `<li data-rfi-request="{key}" data-rfi-state="{state}">` with the frozen `title: request`, the status line and the withdraw form (scenario 9). v1 and `none` cards also list orphans.
- `MISSING_EVIDENCE_RFI_NOTE` and the RFI link stay.
