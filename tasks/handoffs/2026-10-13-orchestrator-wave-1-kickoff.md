## Steps

### 1. Pre-flight (a few minutes)

1. `git -C ~/dpdpa-next fetch origin`. Check PR #142 state with `gh pr view 142 --repo saqlainmmomin/Cyber --json state`.
2. Confirm `origin/main` contains the E4 RFI code (`app/services/rfi_evidence_requests.py` exists). If not, stop and tell Saqlain.
3. Confirm `codex` is on PATH and logged in (`codex login status`). If not, stop and report.
4. Create `~/cyberassess-runs/wave1/` for logs (outside the repo).

### 2. Create the worktrees

For each row in the table above, from `~/dpdpa-next`:

```bash
git worktree add <worktree> -b <branch> origin/main
ln -s ~/dpdpa-next/.venv <worktree>/.venv
cp ~/dpdpa-next/tasks/handoffs/2026-10-13-codex-wave-1-kickoff.md <worktree>/WAVE1-KICKOFF.md
cp ~/dpdpa-next/docs/plans/2026-10-13-001-single-track-implementation-plan.md <worktree>/WAVE1-PLAN.md
```

The two copies are untracked and stay that way. Never run `git add -A` in these worktrees. Do not copy `.env`.

Codex's sandbox can only write inside its worktree. That is why the kickoff and plan are copied in and why Results go to a file in the worktree root.

### 3. Launch the three runs concurrently

One background process per worktree, each logging to `~/cyberassess-runs/wave1/<wp>.log`. Command shape:

```bash
codex exec -m gpt-6.1-sol -c model_reasoning_effort="medium" --sandbox workspace-write -C <worktree> "<prompt>" < /dev/null
```

Prompts (substitute the WP):

- **WP 1.3:** `Read WAVE1-KICKOFF.md in full, then the "Stage 1. Truthful cut" section and "Revision 5 changes" (M5 to M8, C1) in tasks/handoffs/2026-10-10-document-budget-design.md. Execute only "WP 1.3: reads stage 1" in this worktree (branch codex/reads-stage-1). Follow the common rules. DPDPA goldens must pass byte for byte. No Alembic revision. Write results to WP-1.3-RESULTS.md at the worktree root. Do not push, do not open a PR, add no attribution lines. Stop when done.`
- **WP 2.2:** `Read WAVE1-KICKOFF.md in full. Execute only "WP 2.2: statute citations" in this worktree (branch codex/statute-citations). Follow the common rules. Do not edit app/dpdpa/framework.py or rename any id. Write results to WP-2.2-RESULTS.md at the worktree root. Do not push, do not open a PR, add no attribution lines. Stop when done.`

Record the three PIDs. State the expected duration when you start (unknown; first check at 5 minutes).

### 4. Monitor

Loop until all three have exited:

- Every 3 to 5 minutes, check each log tail and each worktree's `git status --short` and `git diff --stat`.
- Post one line per check: which WP, what it is doing (from the log), files changed so far.
- A usage-limit message (`You've hit your usage limit`): do not retry in a loop. Note how far the run got, and finish the mechanical remainder yourself if the code and tests are done, otherwise report.
- No log growth for 10 minutes: inspect the process and the log. If it is hung on a prompt or a sandbox denial, read the message and either fix the cause or restart that run once.
- A sandbox denial on git (index outside the sandbox): expected. Codex leaves changes uncommitted. You commit.

### 5. Verify each result independently

Do not trust a self-reported pass. Per worktree:

1. `git diff --stat origin/main` and compare changed paths to the work package's allowed files. Anything outside it is a finding.
2. Re-run `OPENROUTER_KEY="" .venv/bin/pytest -q` in that worktree. Compare with the baseline Codex recorded. Goldens must be unchanged. Any new skip or xfail needs an explanation.
3. Read the actual logic change, not just the summary. Check each item of the work package's "Done when".
4. Run Sonnet review subagents split by concern (for example, WP 1.1: converted templates versus python label maps versus the guard test; WP 1.3: selection function versus manifests versus card notice). They return findings; you triage.
5. Send real issues back to Codex as a precise fix prompt (not the raw review dump) in the same worktree, then re-verify. At most two fix rounds per WP. After that, report what is left.

Specific traps to check:

- **WP 1.1.** No golden moved. The numeric priority maps in `findings.py`, `approved_report.py` and `board_derive.py` are untouched and listed. `score_band` exists but nothing consumes it. No prompt file edited. The guard test's allowlist is printed.
- **WP 1.3.** Duplicate filenames are told apart by version id. The DPDPA curated path keeps its legacy order. No Alembic revision. The report line is additive and goes through `S()`.
- **WP 2.2.** `app/dpdpa/framework.py`, ids and criteria editorial notes are untouched. Every citation changed is listed with old and new.

### 6. Commit, push, open the PRs

Per worktree, add only the files that WP changed (explicit paths, never `-A`). Commit message: one subject line, a short body, no trailer. Push the branch. Open the PR:

```bash
gh pr create --repo saqlainmmomin/Cyber --base main --head <branch> --title "<title>" --body "<body>"
```

PR body, in this order:

1. What it changes (three to five lines) and the work package id.
2. **Coherence test** (path rule 1): the loop step it touches; what the AI produces; where the auditor sees it; whether they can check it against the original in one click; what it changes downstream. If the answer for a backend-only change is "no auditor-visible change", say so plainly.
3. **Click-through** (3 to 6 steps Saqlain can do in the running app, or "backend only; verify with `<command>`").
4. Checks: test counts before and after, goldens unchanged, held-out answer keys not read, no AI spend.
5. Known conflict: WP 1.1 and WP 1.3 can touch the same line in `app/templates/components/requirement_card_body.html`. Suggested merge order: 2.2, then 1.3, then 1.1.

After each PR is open, call the PR tools: `get_status`, bind it if it is not bound, read CI, and mention that Auto-fix is available. Never poll CI yourself.

If WP 1.1 and WP 1.3 conflict on rebase after the first one merges, that is Saqlain's merge to make; note it in the PR. Do not rebase or force-push over his work.
